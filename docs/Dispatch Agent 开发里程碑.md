# Dispatch Agent 开发里程碑

> 2026-11-15｜技术选型已确认：微信原生小程序 + TypeScript，从零开发业务功能。
> 本文定义各阶段目标和验收口径。当前交付状态、证据与下一步见[开发任务](开发任务.md)。
> 依据：[需求分析文档](./需求分析文档.md)、[项目访谈记录](./Dispatch%20Agent%20项目访谈记录.md)、[技术选型调研](./Dispatch%20Agent%20技术选型与开源调研（核验版）.md)。2026-11-17 已确认本轮优先级，以「MVP 实施顺序」为准。

## MVP 实施顺序

配送员从同一个录单入口添加图片、在小程序内说话或打字，三种输入都能补充同一趟待确认草稿。核对客户、货品、品牌规格、数量、单位和单价后一次确认，生成整趟取货单和按客户划分的送货单。取货按货品、品牌、规格和原单位汇总，箱、袋分行。送货单显示该客户的明细和本次应收，配送员据此自行对账。少送或数量有误时，按实际送达明细和数量核算本次应收。

1. **S6 文字录单和最小 Harness。** 接入真实文字模型，将输入转成草稿明细。缺失或冲突的字段集中让用户补齐，提供手动编辑。业务代码校验字段、算金额和汇总数量，用户确认后出单。同步建立固定账例、人工标准答案和运行记录，自动比对草稿字段、正式单、取货数量和本次应收。
2. **S7 接入图片与语音。** 复用已验证的选图和上传，接入图片识别及小程序内录音转写。三种输入共用同一草稿和确认入口。检查补充材料、识别失败后手工修正、旧结果晚到时保护当前草稿。
3. **用一趟真实订单验收。** 先在现有页面事件、隔离 PostgreSQL 和微信开发者工具流程自测，再用同一部手机提交三种输入。逐项核对仓库要取什么、每个客户要送什么、实际送达后应收多少。模拟与真机结果各自记录。

欠账、实收登记、跨单抵扣、挂账、冲销、复杂历史单处理列为后续扩展。已开发的账务功能有独立记录，MVP 入口只展示与当趟取货、送货和本次应收相关的操作。

## 1. 推进顺序与阶段成果

建议拆成 **9 个里程碑 S0～S8**。每阶段新增一段可操作、可核对的用户流程。前面的功能在后续阶段持续复用，页面、业务规则和数据存取分开，以便把本地模拟数据逐步替换成真实服务。

| 阶段 | 完成后能演示什么 | 主要依赖 | 可交付的结果 |
|---|---|---|---|
| S0 规则与验收样例 | 拿一趟样例，从原始订单推导出单据和正确账目 | 已有需求文档 | 开发边界、关键数据关系、人工标准答案、待决事项 |
| S1 手动录入并正式出单 | 一家客户，从空白草稿录入、预览到确认出单 | S0 | 微信小程序中的第一条可用流程 |
| S2 多客户取货与送货 | 多家出单、汇总取货、按明细送达、数量更正、客户图导出 | S1 | 能用模拟订单演练一趟配送 |
| S3 对账与跨单收款 | 根据实际送达算账，收款抵旧欠款，补款与更正联动 | S2 | 算得清、可追溯的模拟账目 |
| S4 模拟助手完整原型 | 图片、语音、文字模拟录单，集中追问、历史查价、修改和对账 | S3 | **首轮完整可交互原型** |
| S5 真实账户与数据服务 | 登录后保存订单、收款和材料，退出再进可恢复，账号间隔离 | S4；后端与部署选择 | **真实存储下的手动业务流程** |
| S6 真实文字 Agent | 用自然语言录单、补齐草稿并人工确认出单 | S5；模型服务可用 | **文字 Agent + 最小开发者评测** |
| S7 真实图片与语音 | 从微信/相册选图，在小程序内录音，识别后进入同一草稿 | S6；目标安卓手机、真实样本、识别服务 | **可处理真实订单材料的试用版** |
| S8 实际配送验证 | 用一趟真实订单核对取货、逐家送货和本次应收 | S7 | 实测记录、问题修复和下一步优先级 |

下列阶段保留原工程演进和验收目标。S0～S4 完成模拟原型，S5 提供真实存储和手工流程。当前 MVP 从 S6 的文字录单起步，S7 接齐三种输入后，使用真实订单做配送验证。

```mermaid

    S1 --> S2["S2 取货与送达"]
    S2 --> S3["S3 对账与收款"]
```

各阶段都提供可重置的固定案例。后续服务尚未接入时，可以从阶段入口加载明确标识的模拟数据，独立重现这一步的输入和结果。最终完整流程仍从正常录单入口验收。

## 2. 贯穿全程的验收样例

使用一份基础样例，再为异常场景创建独立副本，防止上一项测试的改单影响下一项答案。

| 数据 | 初始内容 | 可核对的结果 |
|---|---|---|
| 客户 A 本单 | 安井水饺，500g，2 箱，历史价 78 元/箱，本次用户确认 82 元/箱 | 本单订单金额 164 元；全部送达后本次应收 164 元 |
| 客户 B 本单 | 同款安井水饺，500g，3 箱，本次 80 元/箱；另有同款 3 袋，每袋 20 元 | 订单金额 300 元；全部送达后应收 300 元 |
| 客户 C 本单 | 另一个品牌的水饺，500g，1 箱，75 元/箱 | 订单金额 75 元，与安井分开汇总 |
| 整趟取货 | 三家订单均已确认 | 安井 500g 为 5 箱、3 袋两行；另一品牌 500g 为 1 箱一行 |
| A 的旧欠款 | 一张早于本单的历史单，尚欠 60 元 | 与本次 164 元分别显示 |
| A 本次收款 | 收到 100 元 | 旧单分配 60 元并付清，本单分配 40 元，剩欠 124 元 |
| A 后续补款 | 再收到 124 元 | 本单累计实收 164 元，剩欠 0；两笔收款各有记录 |

另外准备独立样例：数量从 2 箱改成 3 箱与追加到 5 箱的歧义、B 的 3 袋确未送达、原订 5 箱实收 3 箱、已收 200 元后应收改为 220/180 元、重复上传、识别晚返回、同名客户、跨账号访问。

计算与记录需要区分整趟配送、每位客户的单据、单据明细、版本、配送状态、收款以及收款分配。正式数据对象的命名和表结构留给实现决定，但这些业务关系应在 S0 写清。

## 3. 各阶段实施与验收

### S0｜先让业务规则和标准答案对得上

**范围**

- 按现有需求列出草稿、待确认预览、正式单及更正版本的变化关系。
- 明确订单金额和已送达应收、整趟合计和客户单据、到账和分配的区别。
- 为基础样例和异常样例写人工标准答案，标明每步操作前后哪些记录改变。
- 明确首次录单可边用边建客户、货品，历史价必须按客户和同款货品查找并确认。
- 核查小程序 AppID、开发者权限、目标安卓手机是否可用，记录实际可验证的环境。
- 列出需要在后续阶段确定的业务规则和服务选择，采用第 4 节的处理时点。

**验收方式**：人工走读基础案例，能明确算出三行取货汇总、各客户应收和 A 两次付款的分配。开发者能据此解释“预览未确认”“未送达”“更正已收款订单”的结果。

**完成标志**：核心规则有一致解释，标准答案可作为后续阶段的检查依据。只影响超额款或录错收款的未决项可继续保留，不阻塞录单及配送开发。

### S1｜一家客户，手动录单到正式出单

**完成内容**

- [x] 建立微信原生 TypeScript 工程，提供助手、取货、送货与对账三个页面入口及适当空状态。
- [x] 从空草稿录入客户、货品、品牌、规格、单位、数量和单价，允许直接新建客户和货品。
- [x] 先用手动编辑入口跑通必填校验、金额计算、预览修改、确认出单。
- [x] 持有明确的草稿标识和版本标识，确认后才建立正式单据；保存本地演示状态并提供重置入口。
- [x] 给金额计算、字段校验和确认重复提交准备必要的确定性检查。

**独立验收**：重置为空白 → 填 A 的 2 箱 × 82 元 → 看到预览 164 元 → 返回修改 → 再确认。缺单价时提示补齐；确认前没有正式单；重复点击确认只有一张正式单；重新打开后可找到原有演示数据。

**完成标志**：用户能在小程序里真正生成第一张可核对的单据，预览和正式数据有清楚边界。助手输入此时可先采用明确的演示入口。

**尽早验证的设备事项**：AppID 和目标手机可用时，在这一阶段用最小验证页试通会话选图、相册选图、小程序内显示图片并录音、图片保存。记录权限与中断行为。若暂缺环境，继续完成开发者工具中的业务路径，把设备项明确标为未验证，后续由 S7 补齐。

### S2｜扩展为多客户取货、配送和改单

**完成内容**

- [x] 扩展为同一趟多位客户，全部补齐后一起预览和确认。
- [x] 按客户首次手动录入位置维护顺序。图片批次按 S4 模拟、S7 真实输入推进。
- [x] 正式单按货品、品牌、规格、单位生成取货汇总，展示客户明细和合计。
- [x] 按明细更新未配送/已送达，支持指定客户单据的批量标记。
- [x] 实现数量、价格、未配送货品的更正预览，确认后生成新版本并同步汇总差异。
- [x] 按客户实际导出明细图片，标识版本，长内容按可读尺寸分图。

**独立验收**：加载 A/B/C 草稿 → 补齐并出单 → 取货清单为三行 → 按客户送货 → 更正数量并确认 → 检查客户单据和取货差异 → 导出该客户新版图片。

额外检查相同货品不同客户价格不影响取货数量汇总；品牌不同、箱和袋不同不能合并。原订 5 箱实收 3 箱，须先把数量改为 3 并确认，再按整条标记送达。

**完成标志**：一次确认驱动单据版本和取货汇总同步变化，配送状态属于具体明细，客户图与当前正式版本对应。已送达明细的删除和替换见 [S3 更正规则](PRD.md#84-更正与一致性)。

### S3｜算应收、收款抵旧账、补款和更正

**完成内容**

- [x] 对账时检查未送达项，漏标可补标，确未送达项排除在本次应收之外。
- [x] 分别显示本次应收、本单累计实收、本单剩余欠款和历史欠款，汇总到整趟。
- [x] 每次输入收到金额，生成一笔收款及分配记录，依客户最早欠款顺序抵扣。
- [x] 支持可选旧欠款补录及历史单补款，完成本趟核对后可开始下一趟，旧欠款保留。
- [x] 支持已结清单更正，保留已收款，重算欠款或多收金额。
- [x] 同一操作重试不重复入账；货款和金额计算保留适当精度。
- [x] 在本地业务层验证一次修改的各项结果一致，失败时保留原有结果；S5 再验证服务端事务。

**独立验收**：加载已送达的基础单据，收 A 的 100 元，核对 60/40 元分配和欠 124 元，再补 124 元付清。重复提交第一笔收款，记录数和金额不增加。B 的 3 袋确未送达时，本次应收为 240 元，订单金额仍是 300 元。

在独立案例中，更正已收 200 元单据的应收为 220 元，显示欠 20 元；另一个副本更正为 180 元，显示多收 20 元，多收不自动抵未来货款。取消更正时，原记录保持原值。

**完成标志**：已确认规则覆盖的正常、补款和更正案例都能得到人工标准答案。收款录错和超额新收款按 [S5 记账规则](S5方案.md#5-已确认的记账规则)实现和验收。

### S4｜把流程接到模拟助手，交付完整原型

**完成内容**

- [x] 普通发送支持模拟图片批次、语音转文字和文字输入，转写可编辑，材料连续进入同一草稿。
- [x] 固定样例驱动意图识别，覆盖录单、补充、生成、修改、指定单据送达和收款输入。
- [x] 生成时集中检查缺项，独立问题一起问，依赖规格/单位的问题在答案明确后继续问。
- [x] 查询模拟历史价，展示来源日期；确认沿用才使用，指定新价按新价计算。
- [x] 客户别名经确认关联客户 ID，不能用其他客户的价格或欠款。
- [x] 疑似重复材料跳过并指出内容，可恢复补录；数量追加与改成由用户决定。
- [x] 改单优先定位当前趟，多个候选让用户选，无匹配请指定原单。
- [x] 处理失败可以重试或手动补充，处理进度有实际状态，晚返回结果绑定原草稿及版本。

**独立验收**：先使用仅客户 A 的历史查价案例，从助手首页连续发送材料，用户说生成送货单后再集中追问。历史价 78，本次输入 82，最后出单 164 元，取货 2 箱。再用完整 A/B/C 案例走完配送、收款及更正，整趟取货按第 2 节的三行汇总核对。另选一组案例检查歧义、重复、多个原单候选和失败恢复。

**完成标志**：四环节从正常入口走完，所有功能都落到前面实现的单据和账目。固定样例的模拟能力有可见标识，未覆盖输入可转为手动补充。首次完整原型在此交付，主要评价操作是否顺手、业务是否一致。

### S5｜换成真实账户、存储和服务端业务处理

**范围**。各项实现和验收状态见[开发任务](开发任务.md#当前交付)。

- 服务端校验微信账号归属，订单、聊天、客户、历史价、材料和收款均按账号隔离。
- 草稿、正式单据、版本、配送状态、收款与分配持久保存，重进后恢复。正式出单、更正、收款由服务端统一校验和提交，处理版本冲突及重复请求。
- 支持图片材料上传、任务归属与状态查询，为后续图片识别提供入口。
- 覆盖 S3 财务规则及真实记账前已确认的补充规则。见 [S5 方案](S5方案.md#5-已确认的记账规则)。
- 演示数据有独立归属和环境，备份可恢复订单、版本和收款关系。

**独立验收**：两个测试账号分别录单，服务端无法跨账号读取或修改记录。A 账号退出再登录后，草稿、历史和收款都在。收款提交成功但响应丢失后重试，仅记一笔。模拟提交中途失败，不出现收款写入而分配丢失；两个页面同时提交时不覆盖新版单据或重复抵扣。

**完成标志**：S1～S4 的业务结果在真实存储上仍一致，正常手动录单和收款可独立使用。助手识别仍可加载演示结果，服务端可靠性无需依赖真实模型来证明。

### S6｜先接真实文字 Agent 和最小评测

**完成内容**

- [x] 实现 DeepSeek 文字模型接口，将同一趟的录单与补充整理成草稿字段，标出缺项和冲突；真实调用验收待配置密钥。
- [x] 将确认使用的草稿写入及预览接到现有服务端，校验账号、草稿 ID 和修订号。人工确认才出正式单。
- [x] 沿用业务代码的金额、取货汇总和本次应收规则。模型调用失败时保留输入，可重试或手工补齐。
- [x] 建立最小 Harness，包含固定任务、初始数据、工具执行记录和规则评分，记录运行 ID、模型版本及用例版本。[执行记录](S6文字录单.md#执行记录)

**独立验收**：用自然语言输入「老王要两箱安井水饺 500g」，按提示补上 ¥82 单价。确认后取货单为 2 箱，送货单为 ¥164。客户、箱袋或数量有歧义时，先提示核对；未补齐的单价留空。

评测依据真实调用记录和最终业务状态，检查漏项、重复输入、不明确的修改、模型调用失败和确认前误出单。

**完成标志**：核心案例的业务结果符合标准答案，有失败原因可追踪。固定案例通过只证明已覆盖场景，实际语言变化的稳定性在 S7、S8 持续验证。

### S7｜接图片和语音，组成真实多模态流程

按以下小步执行，每一步保留独立入口和验收结果。

| 子步骤 | 实施内容 | 独立验证 |
|---|---|---|
| S7a 真实图片 | 会话/相册选图，上传和分批处理，关联草稿；图片抽取为字段和待补充项 | 用真实截图及手写照片逐字段对照人工答案；多批材料按原顺序合并；重复片段能提示和恢复；失败可补填 |
| S7b 真实语音 | 小程序内展示已选图片并录音，转写可编辑，确认发送后进入 S6 | 对商品名、品牌、数量、箱袋、单价逐项核对；测试拒绝权限、来电或切出后的中断提示及重新录入 |
| S7c 混合材料 | 图片、文字、语音补充共同参与生成时检查；按草稿和版本处理迟到结果 | 后发语音补上前图缺价后不重复追问；用户已更正数量时，旧任务回包不能悄悄覆盖；发起下一趟后回包不会串单 |

**完成内容**

- [ ] 收集真实原材料及经配送员确认的最终答案，分别保留开发样本和未参与调试的验收样本。
- [ ] 识别、转写使用可替换接口，按真实样本效果确定服务商或模型。
- [ ] 按字段记录错误率、整单补改次数、处理耗时和调用成本，结果带样本数与材料类型。
- [ ] 在目标安卓手机验证选图、录音和短屏下的三种入口与核对操作。

**完成标志**：真实材料能进入同一套预览与确认流程，正式单据与人工答案一致，错误可以通过追问和编辑纠正，关键真机路径已验证。识别效果阈值结合样本与用户容忍度确定，不能用未经测量的“准确”作为通过结论。

### S8｜跑真实配送，检查是否达到使用目标

**完成内容**

- [ ] 先用一趟真实订单做可核对的试用，记录客户数、明细数、图片和语音数量。
- [ ] 从开始导入材料计时，到补充、核对并生成可用单据为止；另外记录配送及对账耗时。
- [ ] 在仓库核对取货汇总，逐家核对送货明细，按实际送达核对本次应收。
- [ ] 记录正常运行、错误恢复、实际改单与次日继续使用的情况。
- [ ] 修复影响取货、送达、金额或恢复的实际问题，并回归被影响的案例。
- [ ] 把已验证结果、剩余问题和扩展优先级写成简短试用记录。

**完成标志**：同一趟真实订单的送货单、取货数量和本次应收与人工核算一致，关键流程能完整走完。记录录入、识别、补充和核对各花了多久，再用不同订单规模复验。
