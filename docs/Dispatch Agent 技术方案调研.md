## 先给三个答案

| 你的问题 | 答案 |
|---|---|
| 有没有合适的 MIT 开源项目能直接二次开发？ | **没有。** 一个一个都对不上，最接近的也缺核心模块。原因见第三节 |

## 一、开源项目盘点（已逐个核实协议）

### A 类：进销存 / 批发订货（想找业务底座）

| 项目 | 协议（读自 LICENSE 原文） | 技术栈 | 有小程序端 | 有应收/欠款 | 活跃度 |
|---|---|---|---|---|---|
| **litemall** | **MIT** | SpringBoot + Vue + **自带微信小程序** | ✅ | ❌ 完全没有 | 2022 年后基本停更 |
| 若依 RuoYi | **MIT** | SpringBoot + Vue | ❌ | ❌ 纯权限脚手架 | 活跃 |
| **ERPNext** | **GPL-3.0** | Python(Frappe) + MariaDB + Vue | ❌ | ✅ **最全**，含账龄 | 活跃（41.3k star） |
| 华夏ERP | Gitee 标 **Apache-2.0**，但多个 fork 标 GPL-3.0 ⚠️ | SpringBoot + Vue2 | ❌ | ✅ 有客户对账 | 活跃 |
| Odoo | **LGPL-3.0** | Python + PostgreSQL | ❌ | 部分（账龄在企业版） | 活跃 |
| Apache OFBiz | Apache-2.0 | Java + Groovy | ❌ | 需自建 | 活跃但极重 |
| mall / CRMEB | Apache-2.0 | Java / PHP 商城 | 部分 | ❌ | 活跃 |

**ERPNext 有个意外发现**：它内置了 `delivery_trip` / `delivery_stop`（配送趟次 + 站点）和 `accounts_receivable_summary`（应收账龄）。这两块正好是这个项目最需要、也最容易被做错的东西。**它值得当参照物，但不值得拿来跑。**

### B 类：单据 OCR / 文档结构化

| 项目 | 协议 | 中文手写 | 输出结构化字段 | 备注 |
|---|---|---|---|---|
| **PaddleOCR**（含 PaddleOCR-VL） | **Apache-2.0** | 支持，无公开准确率 | VL 版可出 JSON | 92.7k star，最稳的选择 |
| RapidOCR | Apache-2.0 | 继承 Paddle 模型 | 纯文本 + 框 | **CPU 上快**，适合省钱场景 |
| Umi-OCR | MIT | 可以 | ❌ 只出纯文本 | 桌面工具，不适合服务端 |
| dots.ocr | MIT | 多语言 | ✅ JSON | 9.2k star，较小众 |
| Docling | MIT | 中文手写弱 | ✅ JSON | IBM 出品，但偏文档不偏单据 |
| MinerU | Apache + **附加商用阈值** ⚠️ | 偏 PDF 文档 | ✅ | 面向论文排版，不匹配 |

### C 类：中文语音转写

| 项目 | 协议 | 中文 | **热词支持**（对本项目最关键） |
|---|---|---|---|
| **FunASR**（阿里达摩院） | **MIT** | 强（Paraformer） | ✅ 有，且官方宣称热词召回率 3% → 79% |
| SenseVoice | MIT | 强 | 未见热词接口 |
| whisper / faster-whisper | MIT | 一般，术语易错 | 无原生热词，只能靠 prompt 偏置 |
| sherpa-onnx | Apache-2.0 | 好 | 有，但**仅 transducer 模型支持** |

**为什么热词是关键**：这个场景里全是"三全""思念""安井""500g""鸡柳"这类专有名词，通用 ASR 最容易错的就是它们。FunASR 的热词表可以直接把这些词灌进去——这是它比 whisper 更适合的唯一决定性理由。

### D 类：Agent 编排

| 项目 | 协议 | 适合"多轮确认 + 可回滚"的流程吗 |
|---|---|---|
| **LangGraph** | **MIT** | ✅ **最合适**。显式状态图 + checkpoint + `interrupt()`，天生就是干这个的 |
| Pydantic AI | MIT | 结构化输出最强，适合做抽取层 |
| OpenAI Agents SDK | MIT | 可以用，但和模型强绑定 |
| Langflow | MIT | 可视化编排，单人项目用不上 |
| Dify | Apache + **禁多租户 SaaS + 禁去 LOGO** ⚠️ | 偏自由对话，不适合固定流程 |
| CrewAI / AutoGen | MIT（AutoGen 要看清 LICENSE-CODE） | 多角色协作，不是状态机，不匹配 |

## 二、四个"假 MIT"陷阱（必须知道）

这些项目看起来开源，实际有附加条款。踩中会很难受：

| 项目 | 陷阱 |
|---|---|
| **Surya / marker** | 代码是 Apache-2.0，但**模型权重是 RAIL-M**（限制商用） |
| **MinerU** | Apache + 附加条款：月活超 1 亿或月收入超 2000 万美元要另买商用许可，且必须标注 "Powered by MinerU" |
| **Dify** | Apache 改版：禁止做多租户 SaaS，禁止去除 LOGO 和版权 |
| **AutoGen** | 根目录 LICENSE 是 CC-BY-4.0（那是文档的），代码协议在 `LICENSE-CODE` 里才是 MIT。**极易误读** |
| **华夏ERP** | Gitee 页面标 Apache-2.0，但有多个 fork 和第三方文章标 GPL-3.0。**要用必须先跟作者书面确认** |

## 三、为什么"没有一个能直接用"

把需求的核心能力列出来，跟候选项目对一遍：

| 核心能力 | litemall | ERPNext | 华夏ERP | 说明 |
|---|---|---|---|---|
| 微信小程序端 | ✅ | ❌ | ❌ | 只有 litemall 有 |
| 客户 + 赊销价格体系 | ⚠️ 只有会员/等级价 | ✅ | ✅ | litemall 是 B2C 模型，没有"这个客户这个价" |
| 送货单（含签收、按客户展示） | ❌ 只有商城发货单 | ✅ | ✅ | |
| 取货单汇总 | ❌ | 部分 | 部分 | 按货品+品牌+规格+单位汇总，要改 |
| **应收台账 + 账龄** | ❌ | ✅ | ✅ | |
| **收款核销 + 跨单抵扣** | ❌ | 部分 | 部分 | **最难的一块**，要"一笔钱拆给多张单"的核销表和反核销 |
| 截图/语音 → 结构化订单 | ❌ | ❌ | ❌ | 三家都没有 |
| 司机视角（一趟车为结算单位） | ❌ | ✅ delivery_trip | ❌ | 又是 ERPNext 独有 |

**结论：没有任何一个项目同时具备这八项。** 最接近的 ERPNext 缺小程序端和 AI 入口；litemall 缺应收、欠款、送货单、核销四大核心。

## 四、改造别人 vs 从 0 写

### 4.1 先纠正一个常见误解：GPL 并不等于不能用

很多人一听 GPL-3.0 就说"传染，不能用"。**这个判断不准确。**

GPL-3.0 的义务只在"分发（conveying）"时触发。你自己部署在服务器上跑，不把二进制发给别人，**法律上不需要开源**（那是 AGPL 才有的网络条款）。

所以：
- 后端用 ERPNext，自己服务器跑，**法律上没问题**
- 但一旦你想部署给别的经销商用，就得开源你的修改
- 你的小程序前端通过 HTTP API 调后端，前端是独立作品，不受影响

**真正该劝退 ERPNext 的不是协议，是工程量**：Frappe 是个重型框架，你得先学会它，再重写整个小程序端，等于两件事都干一遍。

### 4.2 工作量对比

按单人、业余时间估算（人日）：

| 模块 | 从 0 写 | 改 litemall |
|---|---|---|
| 小程序骨架 + 登录 + 文件上传 | 2 | 0（现成） |
| 读懂别人的代码、拆掉 B2C 商城模型 | 0 | **5** |
| 客户 / 货品 / 历史价格 三张表 | 3 | 3（模型要重写） |
| 送货单 + 明细 + 改单留痕 | 4 | 4 |
| 取货单汇总 | 1 | 1 |
| 送货状态 + 客户明细图导出 | 2 | 2 |
| **对账 + 收款核销 + 跨单抵扣** | 5 | 5 |
| 识别链路（上传 / 切段 / 多模态 / 追问编排） | 8 | 8 |
| 语音 | 3 | 3 |
| 升级 Spring Boot 依赖、填停更两年的坑 | 0 | **3** |
| **合计** | **约 28 人日** | **约 31 人日** |

**改造反而更慢。** 原因很简单：它省下的是"你本来就会写的那部分"（脚手架、登录、上传），多出来的是"读懂并拆解别人模型"的成本。而真正花时间的两个大块（对账核销、识别链路）它一个都帮不上。

### 4.3 我的结论

> **业务层从 0 写，识别层用开源/云服务，编排层按需。**

理由有三条：

1. **这个项目的业务复杂度被高估了。** 拆到底就是 5 张表：客户、货品、历史价格、送货单（+明细）、收款（+核销）。没有并发、没有复杂权限、没有多租户。一套对账规则就是纯数学，不是"系统"。
2. **工程复杂度被低估了。** 真正难的是"多模态识别 + 人工确认的流程编排"——让 AI 认出七八成，再用一个顺手的交互把剩下两三成补上。这部分**没有任何开源项目能给你**，也是产品的全部价值所在。
3. **从 0 写没有技术债。** 你一个人维护，两年后回来看自己的代码，比看别人的代码快十倍。

**如果你一定要拿参照物，就拿 ERPNext 的数据模型抄设计**（尤其 `delivery_trip` 和应收账龄的口径），不搬代码。这样既学到东西，又零法律风险。

## 五、推荐的技术栈（给结论，不讲细节）

| 层 | 选择 | 为什么不选别的 |
|---|---|---|
| 前端 | 微信原生小程序 + TypeScript | 见第六节 |
| 后端 | 一个轻服务（Node/TypeScript 或 Python/FastAPI）+ PostgreSQL | 不用 Java/Spring，一个人维护不动那么多样板 |
| 部署 | 优先微信云开发（省掉域名备案和运维）；若需要长任务流式输出，改自建小服务器 | 单人项目的运维成本要压到接近 0 |
| 识别 | **直接调多模态大模型出 JSON**，不要先自建 OCR | 自建 OCR 只给文本，还得再写一层抽取，多一道工序还多一个故障点。PaddleOCR 留作后期降本/离线方案 |
| 语音 | 先用云 ASR（腾讯云/火山，约 1–2 元/小时），不自己部署 | 量太小，自建的运维成本远高于省下的钱 |
| 编排 | 先自己写状态机（5–6 个状态，几百行够）；复杂了再上 LangGraph | LangGraph 的优势在分支多、要 checkpoint 回滚的场景，你这场景前期用不上 |

一句话：**除了"识别"这一环，其他每一层都应该选最不费脑子的方案。** 因为你的精力要全部留给识别和交互。

## 六、跨端框架 vs 原生

这个问题要分两层看，很多人会混在一起。

### 第一层：小程序内部，原生 vs Taro / uni-app

| | 微信原生 | Taro | uni-app |
|---|---|---|---|
| 协议 | 微信平台协议 | MIT | Apache-2.0 |
| 当前版本 | 随基础库迭代 | v4.3.2（2026-11） | uni-app x 5.34（2026-10） |
| 活跃度 | 官方 | 活跃（37.8k star） | 活跃（41.7k star） |
| **对 Skyline 新渲染引擎的支持** | **首发** | 需开"半编译模式" | 官方文档明确写"**实验阶段**" |
| 包体积 | 基准 | 有运行时开销 | 有运行时开销（社区口径大 30%，无权威实测） |

**Skyline 是什么**：微信官方的新渲染引擎，官方数据是首屏渲染时间从 2492ms 降到 2052ms（-17.6%），框架建树到首屏从 626ms 降到 312ms（-50%）。

但对你这个项目，**Skyline 不是必需的**。你的页面最多是 20 家客户 × 5-10 条明细，也就是几十到两百个节点、几十 KB 数据——离 WebView 的性能瓶颈还很远。

**我的选择：原生。**

理由不是性能，是**成本结构**：
- 跨端框架的价值在"一套代码跑多端、多团队协作"。你是**单人、单端**，这两个前提都不成立。
- 它的代价是真实存在的：中间层要跟版本对齐，平台新能力永远慢一步（uni-app 自己都标"实验阶段"），出问题时你要判断"是我的问题还是框架的问题"。
- 你的关键能力（录音、选图、上传、长列表、流式文字）全是平台 API 直连，跨端框架在这里**一点复用收益都不产生**。

> 另外两个别碰：**mpvue** 2022 年就停了，**Remax** 仓库已归档。

### 第二层：小程序 vs 真 App

先说一个必须澄清的：**Flutter 和 React Native 编译不出微信小程序。** 不是工具不成熟，是渲染模型根本冲突——Flutter 用 Dart + Skia 自绘，小程序只接受 WXML/WXSS/JS 在双线程容器里跑，没有能承载自绘引擎的画布。市面上所谓"Flutter 转小程序"的工具，本质是套 WebView 或者重写，不是编译。

所以真正的选择只有：**微信小程序 vs Android 原生（Kotlin + Compose）**。

| 能力 | 微信小程序 | Android 原生 |
|---|---|---|
| 切到微信时继续录音 | ❌ 切后台 5 秒挂起 JS 线程 | ✅ 前台服务可做到（有版本限制） |
| 单次录音时长 | 上限 10 分钟 | 不受此限 |
| 系统悬浮窗 | ❌ 没有 | ✅ 有（但要特殊权限，Android 15 起还要求悬浮窗当前可见） |
| 息屏录音 | ❌ | ✅ |
| 本地通知 | ❌ 只能订阅消息 | ✅ |
| 分发 | 扫码即用、发版即时生效 | 要装 APK，国内商店要软著/备案，厂商会拦截 |
| 更新 | 你改完他下次打开就是新的 | 用户得手动点安装 |

**注意 Android 侧的坑也不小**：Android 14 起禁止开机自启麦克风类型前台服务；Android 15 起"有悬浮窗权限就能后台启动服务"这条豁免还要求悬浮窗当前可见。所以"Android 能做跨应用录音"这句话成立，但代价是权限引导和版本适配，而且用户还得愿意一直给你这些权限。

**我的选择：微信小程序。**

理由不是技术，是场景：
- 用户只有 1–3 个人。**"扫码即用、改完就生效"这一条，价值超过所有技术优势。** 你不用教他们装 APK，不用管厂商拦截，不用每次更新催他们点安装。
- 这个项目里"跨应用录音"是**想要更好**，不是**必须有**。访谈里已经确认的路径——从微信会话选图、在小程序内放大看、同时口述补充——是够用的。
- 唯一会推翻这个结论的情形：核心流程必须是"锁屏或切到别的 App 时连续录几十分钟"。**这个场景不存在。**

### 要不要留后路

要，但成本要提前想清楚。

做法：把订单解析的逻辑、对账规则、数据模型、API 调用全部写成**跟界面无关的纯 TypeScript 模块**；录音、上传、存储这些平台能力封在 adapter 接口后面（小程序侧用 `wx.*`，将来 Android 侧换实现）。

这样可复用的部分是：后端、数据库、业务规则、解析逻辑，**大约 50%–70%**。但 WXML/WXSS 页面在 Compose 里等于重写，前台服务、悬浮窗、通知是全新代码，整体仍相当于重做 60%–70%。

结论：**留接口，但别为了"以后可能转"而现在增加复杂度。** 大概率你不会转。

## 七、我对这些语言的掌握程度

这个问题必须说实话，因为选栈之后出问题时，只有我能帮你 debug。

| 语言 / 栈 | 掌握程度 | 实话 |
|---|---|---|
| **TypeScript / JavaScript** | ★★★★★ | 最强。能写生产级代码，熟悉生态里的坑 |
| **WXML / WXSS（小程序原生）** | ★★★★☆ | 语法简单，写得准。但基础库版本差异、平台 bug 需要现查文档，我不敢凭记忆答 |
| Vue 3 / React | ★★★★★ | 强 |
| **Python** | ★★★★★ | 强。FastAPI、数据处理、调模型都熟 |
| Node.js 后端 | ★★★★★ | 强 |
| **Java / Spring Boot** | ★★★☆☆ | 能写，但样板代码多。版本兼容（SB2 vs SB3、MyBatis vs JPA）容易出细节错 |
| **Kotlin / Jetpack Compose** | ★★★☆☆ | 能写。但 Compose 的最佳实践和 Android 版本适配我会出错，需要你实机验证 |
| Dart / Flutter | ★★★☆☆ | 能搭 widget 树，性能调优偏弱 |
| Go | ★★★☆☆ | 能写 |
| Swift / iOS | ★★☆☆☆ | 弱，不建议依赖我 |
| C++ / Rust | ★☆☆☆☆ | 只能读，不建议让我写 |

**一句实话**：栈越冷门，我越容易犯"能编译但不对"的错——语法我永远写得出来，但生态细节、版本坑、平台怪癖，我需要查资料，而且可能查不到。

所以"我熟不熟"应该作为选栈的一个**真实权重**，不是客套话。你一个人维护，这块的权重比"社区 star 数"更高。

## 八、一句话总结

> **从 0 写一个微信原生小程序，业务层自己写（5 张表），识别层直接调多模态模型，语音先用云服务，编排先自己写状态机。**
>
> **不改造任何开源项目**，但把 ERPNext 的配送趟次和应收账龄模型当参照物抄设计。

理由汇总成一句：**这个项目的难度 90% 在"识别 + 人工确认的交互"，10% 在业务代码。所有开源的、跨端的、原生的争论，都应该服从于把精力留给那 90%。**
