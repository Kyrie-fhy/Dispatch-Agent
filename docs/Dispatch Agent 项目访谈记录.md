# Dispatch Agent 项目访谈记录

更新日期：2026-11-15。已合并本轮补充访谈；同一事项以本文整合后的规则为准。

配送员每天从微信聊天和手写单里整理速冻食品订单，再去仓库取货、逐家送货和对账。目前主要靠手写单，偶尔打印。Dispatch Agent 希望让配送员用图片、语音和文字直接录入订单，由助手整理送货单、生成取货清单，并核算每家客户本次应收、实收和欠款。

以下问答按主题整理。「已确认」记录访谈中确定的规则，「建议」记录讨论过的做法，「待确认」记录尚未决定的事项。

## 现有做法与 MVP 范围

**Q01｜配送员现在怎样整理订单和核算应收？**

**A｜现状。** 客户通常在晚上通过微信文字或语音陆续下单。配送员需要在第二天早上出发前，把多位客户的碎片信息整理成完整的手写送货单，以便到仓库取货、逐家送货。每晚整理通常花三四个小时，是当前最主要的负担。单据会写客户名称、货品、规格、数量、单价和总价；配送后再对照送货单，逐家核对实际送出的货品、单价和数量，手动计算本次应收，这一步也很费时。遇到简称时，配送员凭记忆或翻历史聊天判断。

**Q02｜每天的订单规模多大，希望把整理时间缩短到多少？**

**A｜已确认。** 每晚客户少时五六家，多时约二十家；每位客户通常订 3～10 种货品。MVP 希望把每晚整理订单的时间控制在一小时以内，理想是半小时。

**验收建议。** 时间从开始导入材料算起，包含补充信息、核对和修改，直到生成可用单据。按客户数和货品数估算约为 15～200 条明细，可作为模拟原型的规模参考；这不是实测订单分布。

**Q03｜第一次使用前，需要先维护客户和商品档案吗？**

**A｜已确认。** 要能从第一笔真实订单直接开始。系统预先定义客户、公司、货品、规格、数量、价格等字段，再用上传的材料和用户补充填入数据。客户、货品和历史价格随使用积累，省去事前逐条维护商品档案的工作。现有材料主要是微信聊天记录，其次是手写订单。

**Q04｜第一版覆盖哪些工作？**

**A｜已确认。** 产品有三个模块。聊天助手处理录单、识别意图、补充缺项和生成送货单。取货模块告诉配送员去仓库拿什么、拿多少。送货模块按客户展示明细，支持标记送达，并在送货单里完成对账。第一版要覆盖录单、取货、送货、对账四个核心环节。

**Q05｜配送流程由谁操作，数据怎么隔离？**

**A｜已确认。** 同一个人负责录单、取货、送货和登记实收。不同配送员各自登录，业务数据和聊天记录按账号独立。

## 手机端与输入方式

**Q06｜配送员需要怎样录入原始订单信息？**

**A｜已确认。** 支持上传微信聊天截图和手写单照片，也支持语音输入和打字。比如手写字识别不准，或者微信截图只显示一条尚未转成文字的语音消息时，配送员可以自己口述或打字补充。语音转成文字后，建议允许配送员编辑，再通过普通的「发送」按钮提交。

**Q07｜Android App、微信小程序和 H5，分别能支持什么体验？**

**A｜访谈讨论。** Android App 需要安装，但可以在助手内开始录音，切到微信或相册后用 Android 麦克风前台服务继续录音。系统悬浮窗可以让用户在其他应用上操作控件，也涉及额外权限。微信小程序分享方便，支持选图和小程序内录音。H5 可以直接用链接打开，适合页面内选图、打字和录音，切出页面后的录音表现则取决于浏览器。 [Android 麦克风前台服务](https://developer.android.com/develop/background-work/services/fgs/service-types#microphone) · [Chrome 页面生命周期](https://developer.chrome.com/docs/web-platform/page-lifecycle-api)

**Q08｜在小程序开始录音，再切回微信原聊天点开图片，能边看边录吗？**

**A｜访谈讨论。** 切回原聊天时，微信可以仍在前台，但小程序已经进入后台。公开资料和录音库的开发记录显示，后台录音存在暂停的情况。访谈期间未在目标安卓手机上验证这条流程。另一种做法是通过微信会话选图，把图片带到小程序内查看和录音。需要看图片前后的聊天文字时，可以导入聊天截图。 [小程序运行机制](https://intl.cloud.tencent.com/zh/document/product/1219/61738?lang=zh) · [录音库开发记录](https://github.com/xiangyuecn/Recorder/blob/master/app-support-sample/README.md) · [微信会话选图接口](https://developers.weixin.qq.com/miniprogram/dev/api/media/image/wx.chooseMessageFile.html)

**Q09｜第一版选什么产品形态？**

**A｜已确认。** 做微信小程序，在安卓手机上使用。可以从微信会话选图，也可以从相册导入截图。在小程序内放大或翻看已选图片，同时录音补充订单信息。用户确认这条路径满足日常需要。 [微信相册选图接口](https://developers.weixin.qq.com/miniprogram/dev/api/media/video/wx.chooseMedia.html)

## 录单、追问与正式出单

**Q10｜多位客户排在同一张送货单里时，怎么排序？**

**A｜已确认。** MVP 按微信订单截图的上传顺序排列客户。按 A、B、C、D、E 的顺序发图，送货单就按这个顺序列出对应客户。

**Q11｜单次图片数量有上限时，怎么处理同一趟的多批截图？**

**A｜已确认。** 同一趟可以分批发送。助手按顺序处理，上一批处理完再处理下一批，各批识别结果归入同一张送货草稿。例如 12 张可以先发 6 张，再发 6 张。6 张是访谈里的举例，实际单批上限待确定。

**Q12｜普通「发送」和「生成送货单」分别做什么？**

**A｜已确认。** 聊天使用普通的「发送」按钮，配送员可以连续发图片、文字和语音。等配送员说「生成送货单」，助手再检查当前草稿的全部材料，集中追问仍缺的信息。后发的图或语音可能已经补全了前几批的缺项，发送其中一批素材后可以继续录入。

**Q13｜待补充问题可以一次全部问完吗？**

**A｜建议。** 先处理整批材料，再把当前可以独立回答的问题按客户一起问。依赖前一个答案的问题，在依赖项明确后再问。例如客户 A 的水饺有两种可能规格，可以先问 A 要哪种规格，同时问客户 B 缺失的数量。等 A 的规格和计价单位明确后，再查对应的历史单价。如果用户一次给出规格和本次价格，两项可以一起补齐。前端可先显示「正在识别图片」，再显示「正在整理待补充项」。补充后只需重新检查受影响的明细。

**Q14｜这次订单没写单价，但有历史单价，助手怎么处理？**

**A｜已确认。** 助手自动查找同一客户、同一货品、同规格和计价单位的历史单价，再问配送员本次是否沿用。用户确认后使用该价。用户给出新价时，本次按新价计算。

**Q15｜历史单价需要点开整张旧单才能核对吗？**

**A｜建议。** 第一版在询问里给出历史价格、计价单位和来源日期，例如「客户 A 上次订同规格水饺是 ¥78/箱，这次沿用吗？」系统保存来源单号，开发时也能查证匹配结果。点开整张旧单的入口可以后置。

**Q16｜一位客户先说要 2 箱，后来又说要 3 箱，如何判断最终数量？**

**A｜现状与建议。** 实际工作中，配送员根据聊天上下文和自己的理解先整理数量，然后发给客户确认，有异议再改。助手遇到这种歧义时，可以在集中追问中并列原话，请配送员确认是「改成 3 箱」还是「追加到 5 箱」。客户确认仍由配送员在微信里沟通。

**Q17｜整趟配送有五家客户，只有一家还有字段缺失，能否先给另外四家出单？**

**A｜已确认。** 保留同一趟配送的草稿，所有客户的信息补齐后一起预览和出单。例如有一家的商品品牌还没确定，就先请配送员补齐，再生成整趟的正式送货单。

**Q18｜生成或修改送货单之前，都要预览吗？**

**A｜已确认。** 新建和更正都要先展示预览，配送员能核对和修改。修改后重新展示预览，用户确认后才生成正式送货单。即使助手第一次就识别齐全，也要经过预览确认。正式送货单是后续生成取货单的依据。

**Q19｜是否需要同时整理多趟配送草稿？**

**A｜已确认的现状。** 一般先把当天的账对完，再整理第二天要送的订单，不会同时整理今天和明天的订单。对完账不等于所有客户都已付清，仍可能存在欠款。

**范围建议。** MVP 先保留一张正在整理的配送草稿，不把多草稿并行作为必要功能。历史送货单仍可查询、更正和补记收款。图片、文字、语音及延迟返回的识别结果应归入其原本所属的草稿。

**Q20｜客户发来追加或修改消息，怎样找到原单？**

**A｜已确认。** 配送员直接把新消息告诉 Agent，不必先打开原单。MVP 优先匹配当前这趟配送里的客户订单：只有一张匹配时，生成修改预览，确认后生效；有多张可能匹配时，列出日期、客户和货品摘要，让配送员选择；没找到时，请配送员指定原单，不自动作为新订单。

**Q21｜重复上传截图，或新截图包含已录入内容，怎么办？**

**A｜已确认。** 对疑似重复的订单先跳过并提示。

**交互建议。** 提示具体跳过了哪些内容，方便配送员发现误判后补录。

## 客户和货品怎么识别

**Q22｜「老王」和「王记餐饮」是同一家，要不要记住？**

**A｜已确认的体验与实现建议。** 用户希望建立关联。建议用客户表保存客户 ID、所属账号和单据显示名称，再用客户别名表记录用户确认过的叫法。确认「老王」就是「王记餐饮」后，同一账号下遇到唯一匹配可以沿用。送货单、历史价格和欠款按客户 ID 关联。客户和别名随录单积累。

**Q23｜同一个微信联系人经常替多家店分别下单和对账吗？**

**A｜现状。** 这种情况不太遇到，基本上是客户给自己家下单。访谈以这个常见场景为主。

**Q24｜客户叫不出具体品名，只说「最便宜的羊肉卷」，怎么识别？**

**A｜现状与建议。** 不同客户对同一货品可能有不同叫法。有的能说出具体产品，有的只记得价格或相对便宜的那款。目前配送员凭下单信息和经验判断。助手可以根据这个客户的历史订单给出候选，再请配送员确认。用户确认过的固定简称可考虑记作商品别名。「最便宜的」随当次上下文判断。

**Q25｜两款货品名称和规格相同，仓库靠什么区分？**

**A｜已确认。** 写清品牌。仓库有两款同为 500 克的羊肉卷时，要用具体品牌区分，送货单和取货单都应能明确对应到哪一款。助手识别不到品牌时先请配送员补充。

**Q26｜首次使用还没有历史价格时，单价从哪里来？**

**A｜已确认的现状。** 配送员凭记忆或查看价格表确定单价。同一款货品会因客户不同而有不同成交价，不能把一个客户的价格直接套给其他客户。

**交互建议。** 首次录单允许配送员补充单价，或提供价格表作为查价依据；价格表的具体导入方式尚未确定。有历史价格时，仍按同客户、同货品、同规格和计价单位查询，并经确认后使用。

**Q27｜计价是否涉及称重、整单优惠或其他费用？**

**A｜已确认。** 货品全部按箱、袋等固定单位计价，暂不考虑取货称重。本次应收始终等于已确认送达明细的「数量 × 单价」之和，不涉及整单优惠、抹零或另收运费。

## 取货

**Q28｜取货单从哪里来，要列清哪些内容？**

**A｜已确认。** 取货单从正式送货单提取并汇总，重点列出货品、规格和数量。存在同名同规格的不同品牌时按品牌区分，保证配送员在仓库能拿对货。配送员只需要查看汇总清单，第一版不需要逐项勾选「已取货」。

**Q29｜同规格货品有 2 箱和 3 袋，怎么汇总？**

**A｜已确认。** 保留原单位名称，按货品、品牌、规格和单位分别汇总。同规格的水饺有 2 箱和 3 袋时分两行列出，各用原单位。

**Q30｜正式送货单修改后，取货单怎么更新？**

**A｜已确认。** 确认新版送货单后同步更新取货单，并显示哪些货品或数量发生变更，方便已经开始取货的配送员核对差异。

**Q31｜到仓库才发现缺货，第一版怎么处理？**

**A｜已确认。** 现场由配送员自行决定和沟通处理方式，产品先不干预。取货模块根据已确认的送货单列出应取货品和数量。若现场处理导致数量、货品等变化，配送员事后把变更告诉 Agent；Agent 生成更正预览，用户确认后更新送货单、取货单和本次应收。

## 送货与客户核对

**Q32｜送货时，配送员需要看到什么？**

**A｜已确认。** 正式送货单按客户展示货品、品牌（需要区分时）、规格、带原单位的数量、单价、每条金额和客户合计，配送员据此逐家送货。

**Q33｜配送状态按客户记录，还是按每条货品明细记录？**

**A｜已确认。** 按每条货品明细记录，配送员可以手动编辑「未配送」「已送达」等状态。忙的时候可以用语音告诉助手，把指定送货单的全部明细标为「已送达」。

**Q34｜原订 5 箱，现场只收 3 箱，第一版如何记录？**

**A｜已确认。** 不做专门的部分送达流程，现场仍由配送员自行处理。事后配送员告诉 Agent 实际变更，通过预览确认把原明细数量从 5 箱更正为 3 箱，再按更正后的已送达明细计算本次应收。配送状态仍按整条明细记录；如果没有更正数量，只把原来的 5 箱标为已送达，系统仍会按 5 箱计算。

**Q35｜配送员如何把某位客户的明细发给对方核对？**

**A｜已确认。** 正式送货单生成后，支持按客户导出明细图片，配送员在微信里手动发给对应客户。需要更正时，先预览和确认新版本，再导出修改后的图片。仓库取货和客户交接用手机查看单据、微信发送明细图片即可，第一版无需打印纸质单据。

## 对账、补款与历史单更正

**Q36｜点「一键对账」后，未送达的明细怎么办？**

**A｜已确认。** 每张送货单有「开始对账」或「一键对账」入口。系统先检查明细的配送状态，提醒配送员核实未送达项。已经送到但忘了标记的，可以手动补标，也可以让助手帮忙更新。核实后按「已送达」的明细计算本次应收，确实未送达的货品排除在本次金额之外。

**Q37｜客户少付了钱，需要展示哪些金额？**

**A｜已确认。** 每位客户展示本次应收、本单累计实收和本单剩余欠款，并按送货单汇总。新单还需要展示该客户之前累计欠了多少，与本次应收分开。比如本单应收 300 元、分配到本单的实收为 200 元，本单剩余欠款为 100 元。历史欠款和本单欠款共同用于追款，但不能把历史欠款重复计入本次货品应收。

**Q38｜客户付款或补款时，如何登记并分配到各张单？**

**A｜已确认。** 每次输入「本次收到多少钱」，由系统自动累加并分配，配送员不用手算累计实收。收到款项后，默认先抵扣该客户最早的欠款单，依次抵扣，剩余金额再用于本次货款，并更新各张单据的累计实收和剩余欠款。客户补款也沿用这条规则。

**规则更新。** 原访谈中「直接修改原单累计实收」已由本次收款录入和跨单分配规则替代。是否提供独立的收款流水查看页面尚未确认；不能据此省略实现跨单分配所需的收款与分配记录。

**Q39｜使用系统之前已有的欠款，需要一开始全部录入吗？**

**A｜已确认。** 默认先不处理，由配送员自行决定。对账时如果需要，再补录旧欠款，纳入该客户的欠款和后续抵扣范围。

**Q40｜客户收到明细图后指出单价有误，怎么更正？**

**A｜已确认。** 配送员可以直接告诉 Agent 修改内容，由它按前述匹配规则定位原单；也可以从对应历史送货单进入修改。助手生成新版预览，用户确认后生成更正版本，重算应收和欠款，再按客户导出更新后的明细图片。

**Q41｜已经付清后，新的价格应该进新单，还是更正原单？**

**A｜访谈约定。** 如果原价是双方确认过的，客户也已按原价付清，今后新订的货按新价开单，不因此改动原单。新收到的款项按前述最早欠款优先规则分配到各单。如果同一批货实际谈好的价格被写错，则更正原单。MVP 支持更正已结清的单，并保留该批已收到的钱。比如累计实收 200 元，更正后应收 220 元，就显示还欠 20 元。

**Q42｜更正后发现多收，第一版要登记退款吗？**

**A｜已确认。** 显示多收金额即可。比如更正后应收 180 元、累计实收 200 元，标出「多收 20 元」。由配送员自行处理，不自动抵扣后续新货款。退款登记不在 MVP 范围内。

## Agent 进度与开发评测

**Q43｜配送员在小程序里希望看到怎样的处理过程？**

**A｜用户提出的方向。** 助手识别用户是录单、补充信息、出单还是改已有单据。用户希望看到 Agent 的调用链路，按节点展示处理过程，做完一项就打勾，回答用流式输出。讨论中的做法是把实际动作、结果和判断依据显示为业务进度，例如「正在识别图片」「正在整理待补充项」「找到历史单价 ¥78」「等待确认送货单」，方便配送员判断什么时候需要接手。

**Q44｜用户为什么提出 Harness，最小结构包括什么？**

**A｜用户提出的方向。** 用户用 `Agent = Model + Harness` 概括自己的理解，希望把 Agent 放进可运行、可记录、可评分的环境，能追查它用了哪些工具、工具返回了什么，以及结果为何成功或失败。最小评测结构有五部分。

- **Task** 给出任务输入和目标。
- **Environment** 提供固定的文件、订单或数据库初始状态。
- **Tools** 定义 Agent 可调用的接口。
- **Trace** 记录工具名、参数、实际结果、错误和关键事件。
- **Grader** 依据工具证据和任务结果打分，第一版可用规则或脚本。

**Q45｜README 示例里的评分规则应该怎么改？**

**A｜访谈讨论。** 原示例要求 Agent 读 README，判断项目是否支持插件系统。正确答案里的「不能确认支持插件系统」本身包含「支持插件系统」，用禁止子串的方式会误判。建议将任务限定为根据 README 判断证据是否充分，对结构化结果 `insufficient_evidence` 评分，并从 Trace 核对是否成功读取了指定 README。是否调用 `list_files` 可以留作效率诊断。Trace 应直接由执行工具的代码记录，每次运行保留运行 ID、用例和模型版本，并从固定数据开始。

**Q46｜配送 Agent 第一条评测用例可以怎么写？**

**A｜建议。** 模拟某客户订两箱同规格货品，订单材料没写价格，历史单价是 78 元一箱。助手应查出历史价并询问是否沿用。模拟用户说「这次按 82」，预览金额应为 164 元。评分器还要检查预览确认前只有草稿，确认后确实生成正式送货单，取货单列出两箱。通过工具记录和单据状态，可以区分查价错误、价格用错、提前出单和评分误判。 [Agent 评测中对执行记录和结果的区分](https://www.anthropic.com/research/demystifying-evals-for-ai-agents)

**Q47｜第一版 Harness 给谁用？**

**A｜已确认。** 第一版用于开发者评测。访谈中将 Agent 的运行和评测分开讨论。运行时处理输入、协调工具调用、执行确认规则并记录事件。评测时给同一个 Agent 提供固定任务和数据，检查工具调用、对话与最终单据状态。两者可以复用工具和 Trace，配送员在小程序中看到业务处理进度。

## 验收与交付

**Q48｜做到什么程度，才能替代手写单？**

**A｜已确认的验收目标。** 图片和语音的识别要准确，配送员能便捷录入一手订单信息。确认后生成完整的送货单和取货单，仓库能按货品、规格和数量拿货，配送时能按客户核对货品、规格、数量、单价和总价，对账时能看清本次应收、实收和欠款。建议用同一趟配送走完四个环节，分别核对原始材料里的明确字段，以及经补充、确认后的正式单据。

**Q49｜手头有可以对应原始微信订单和最终手写单的真实样本吗？**

**A｜现状与建议。** 暂时没有。建议先准备模拟订单和人工核算的标准答案，覆盖完整业务流程。真实图片、现场语音的识别准确性，留到拿到真实样本后再验证。

**Q50｜先做可交互原型，还是直接做能试用的微信小程序？**

**A｜已确认。** 第一份交付先用模拟数据制作可交互原型，验证录单、取货、送货和对账的完整操作流程。微信小程序仍是目标产品形态。

**验证边界。** 模拟原型用于验证操作流程和规则一致性，不能证明真实图片、语音识别准确性，也不能证明实际整理时间已降至一小时。识别效果和省时目标需在后续接入真实能力、取得真实订单材料后验证。
