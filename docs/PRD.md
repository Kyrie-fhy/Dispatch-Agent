# Dispatch Agent 开发 PRD

2026-11-15｜当前细化范围为 S1 手动录单、预览与确认。S2～S8 按各阶段开始前细化。技术选型已由用户确认，页面与校验细节属于本次实施选择，待用户体验验收。

## 1. 产品与需求来源

面向一人完成录单、取货、送货和收款的速冻食品配送员。目标为安卓微信小程序，第一份完整原型在 S4 交付。总体功能、业务规则和扩展优先级以[需求分析文档](需求分析文档.md)为总览，以[项目访谈记录](Dispatch%20Agent%20项目访谈记录.md)的已确认规则为准。

本文件补充可执行细节，避免复制全部需求正文。原始分析和技术调研保留为背景材料。需求冲突先标出来源与差异，按用户当前指令或访谈已确认规则处理。

## 2. 页面和阶段

| 页面 | S1 可用操作 | 后续增量 |
|---|---|---|
| 助手 | 单客户手动草稿、添加/移除明细、填入样例、预览、返回修改、确认、开始下一张、重置演示 | S4 模拟聊天与追问，S6 文字 Agent，S7 图片/语音 |
| 取货 | 显示 S2 待接入的说明和助手操作提示 | S2 正式单汇总、品牌规格单位区分、改动提示 |
| 送货与对账 | 浏览本机正式单列表，显示客户、标识及订单金额 | S2 明细送达，S3 应收与跨单收款 |

S1 支持一家客户的多条货品，保持一张活动草稿。确认后可查看正式单或开始下一张。后续多客户整趟关系在 S2 扩展；历史订单继续保留。

## 3. S1 输入和校验

| 字段 | 输入行为和规则 |
|---|---|
| 客户 | 必填，输入显示名称，确认时去除首尾空格；本阶段不要求先建档 |
| 货品、品牌、规格、单位 | 必填文本；单位可手填箱、袋等，默认箱；确认时去除首尾空格 |
| 数量 | 当前实施范围为正整数箱/袋，拒绝零、负数、小数及非数字 |
| 单价 | 元，必须大于零，最多两位小数；换算为整数分计算 |
| 金额 | 明细数量乘单价，各明细加总。超出安全整数范围时提示，禁止出单 |

正整数数量与正单价是 S1 演示范围选择。若真实业务存在半箱或赠品，需补充需求后扩展。客户和货品信息直接随单保存；独立客户 ID、别名与历史查价在 S4/S5 接入，避免把同名自动判为同一客户。

## 4. 操作与状态

1. 首次打开创建空草稿，包含一条空明细。每次编辑保存本地草稿，保存失败时保留页面输入并提示。
2. 添加明细生成新明细 ID，移除时至少保留一条。填入验收样例将当前草稿替换为客户 A、安井水饺 500g、2 箱、82 元。
3. 点击预览先保存当前输入并校验。缺字段或金额不合法显示具体提示，正式单列表不增加。
4. 预览列出客户和每条货品、数量、单价、金额、合计。返回修改后再次预览；任何编辑使旧预览失效。
5. 点击确认使用预览对应草稿 ID 和 revision。草稿版本已变化时要求重新预览；成功后生成正式快照并显示确认结果。
6. 重复确认同一草稿返回已有正式单，不增加订单。已确认草稿不能继续覆盖正式单。
7. 开始下一张生成新的草稿 ID，历史正式单保留。
8. 重新进入恢复活动草稿与正式单；读取到未知格式或损坏数据时提示并保留原值。重置演示需在弹窗中确认，会清除本机演示草稿和订单。

S1 的正式单显示订单金额。配送状态和已送达应收到 S2/S3 实现，不能把订单金额当成已送达应收或已收款。

## 5. 异常与验收

校验错误可直接编辑纠正。写入失败时保持原有正式数据，允许重试。旧草稿写入或旧预览确认被拒绝，提示重新打开或重新预览。开发者应能从标准案例和自动检查定位原因。

详细步骤见[S1 验收](S1验收.md)。本阶段金额、确认状态和重试通过自动检查；微信模拟器、屏幕展示、触控和安卓真机需另行记录实际结果。

## 6. 后续规则处理

S3 前明确同日欠款单排序、已送达明细替换/删除的状态。S5 前明确收款录错、超额收款、历史分配重排，并选定后端和数据库。S6 确定文字模型与工具接口。S7 确定真实材料样本、识别服务及可接受效果。具体时点沿用[开发里程碑](Dispatch%20Agent%20开发里程碑.md)。
