# S5 微信账户与数据服务方案

S5 要让配送员用微信进入自己的账本，换设备或重进小程序后继续录单、取货、送货和对账。本页保留设计和验收标准，交付状态见[开发任务](开发任务.md)，现有接口和启动步骤见 [S5 本地联调](S5本地联调.md)。

## 1. 技术选择

选用 **Node.js／TypeScript API 和 PostgreSQL**。服务端按步骤复用 S1～S4 的业务规则。订单版本和可重试请求由唯一约束保护。收款接入后，收款、分配与请求结果将在同一个事务中提交。有关数据库能力见 [PostgreSQL 事务](https://www.postgresql.org/docs/current/tutorial-transactions.html)、[约束](https://www.postgresql.org/docs/current/ddl-constraints.html)和[锁](https://www.postgresql.org/docs/current/explicit-locking.html)。

本地和 CI 先用同一主版本的 PostgreSQL 验证。独立的微信试用环境首选腾讯云 CVM、同地域同 VPC 的托管 PostgreSQL 和私有对象存储。试用时 API 将提供 HTTPS 入口，数据库走内网。现有测试号用于 S4 预览。S5 接入前需核对 AppID 的后台权限、可用域名、AppSecret 的服务端配置方式和两个测试微信账号。试用环境选型在配置和报价核实后落地。见 [腾讯云 PostgreSQL 内网连接](https://cloud.tencent.com/document/product/409/40429)及[备份和恢复](https://cloud.tencent.com/document/product/409/94889)。

也评估了微信云开发的原生云函数和文档数据库。它能简化小程序身份接入，对本项目需另外验证订单、收款、分配的多记录事务和约束。本轮沿用已调研的 PostgreSQL 路线。见 [CloudBase 小程序云函数](https://docs.cloudbase.net/recipes/add-cloud-function-wechat-miniprogram)及[事务接口](https://docs.cloudbase.net/database/transaction)。

## 2. 微信试用阶段的登录与隔离设计

1. 小程序用 `wx.login` 获取一次性凭证，交给 API。服务端调用微信 `code2Session`，以 AppID 和 OpenID 唯一定位内部账号，签发本系统的短期会话凭证。AppSecret 和微信 `session_key` 留在服务端。凭证过期时重新获取微信登录码，原账本从同一内部账号恢复。参考[微信小程序登录](https://developers.weixin.qq.com/miniprogram/dev/framework/open-ability/login.html)、[小程序网络要求](https://developers.weixin.qq.com/miniprogram/dev/framework/ability/network.html)及[腾讯云登录实践](https://intl.cloud.tencent.com/zh/document/product/1219/68263)。
2. 每个业务请求由服务端从会话取得 `account_id`。客户、草稿、正式单、明细、聊天、材料、收款和分配都按账号保存。数据库外键同时包含账号和业务 ID，查询明确带账号范围。业务数据库角色通过行权限再校验账号，每个事务设置的账号上下文随事务结束清除。见 [PostgreSQL 行权限](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)。
3. 同一微信账号重进时恢复云端活动草稿和正式记录。切换账号清掉屏幕上的上一账号数据，并丢弃上一账号在途请求的响应。首轮联网保存失败时保留正在编辑的输入并显示未保存，用户重试原操作。草稿版本冲突时保留当前输入和服务端版本，用户核对后再提交。退出清除本地会话，服务端撤销该凭证。
4. S4 本地演示数据继续保留在原模式。S5 用独立试用环境和配置，以空账本开始。样例由测试数据脚本初始化，生产恢复在独立库验证。导入旧账如有需要另定来源、确认方式和重复检查。

## 3. 业务接口

当前本地接口见 [S5 本地联调](S5本地联调.md)。服务端微信会话接口和真机准备见 [S5 微信试用](S5微信试用.md)。微信端计划通过 `services` 接入，沿用页面上的预览与人工确认。

| 待实现接口 | 主要用途 |
|---|---|
| 分页历史查询 | 按趟查历史。指定 ID 读取客户单及配送明细的接口已可本地联调 |
| `POST /v1/messages`、`POST /v1/materials`、`GET /v1/materials/{id}` | 保存会话及材料状态。材料上传由 API 校验归属，识别任务绑定账号、原草稿和修订号 |

每个写请求有 `requestId`。服务端按账号和请求 ID 保存操作类型、请求内容摘要及成功结果。相同请求重复到达时返回第一次结果。相同 ID 换内容时返回冲突。手机超时后先重发原 ID 和原内容，重新编辑后再生成新的 ID。需要预览的确认携带服务端预览标识，预览记录账号、对象、输入和相关版本。

## 4. 事务约定

草稿、正式出单和账目写入采用账号工作区行锁及版本校验，落库细节见[技术方案](技术方案.md#22-s5-postgresql-服务)。

- **送达与更正**　用正式单版本、配送修订号和影响账目的记录验证预览。更正写入新版本，保留原版本和原实收，重新计算取货和应收。
- **记收款**　服务端按已确认的最早欠款优先规则计算。收款记录、各单分配和已完成请求记录一起写入，任一步失败则全部回滚。应收、已分配和余额均以整数分计算。
- **材料上传**　数据库保存文件归属、上传状态和对象引用。对象上传成功后再标记可用。识别写稿时检查账号、草稿和修订号。S5 验证状态及归属，真实识别留在 S6 和 S7。

## 5. 已确认的记账规则

用户于 2026-11-16 确认按以下规则执行。S1～S4 已确认规则继续有效。本节作为 S5 后续收款实现的验收依据。

| 实际情况 | 确认行为 | 核对例子 |
|---|---|---|
| 把收到的 ¥90 误录为 ¥100 | 保留原收款记录。冲销错误记录，再生成一笔正确的收款与分配。已有后续收款时先预览受影响的单据和金额，确认后处理 | 旧欠 ¥60，本单应收 ¥164。更正为 ¥90 后分配 ¥60 和 ¥30，本单欠 ¥134 |
| 实际收到的款超过全部欠款 | 已欠部分照常分配，超出部分单独记在客户账上，等配送员明确处理 | 共欠 ¥164，实收 ¥170。欠款结清，另留 ¥6 待处理 |
| 已收过款的旧单后来改价 | 保留原收款分配，按新应收显示该单的多收或欠款。保留人工跨单调账需求供后续评估 | 原应收 ¥60、已分配 ¥60。改成应收 ¥50 后旧单显示多收 ¥10，另一张单原有欠款保持原值 |

若错录之后还有其他收款，先在冲销预览中列出受影响的单据与金额。需要改变后续分配的场景，开发时另列账例确认。

## 6. 开发顺序与通过标准

| 顺序 | 交付内容 | 通过标准 |
|---|---|---|
| 1. 本地服务 | PostgreSQL 迁移、开发会话、草稿 API、服务端业务命令入口 | 用两个本地测试身份各自保存并重读草稿。服务重启后数据仍在。用 B 账号访问 A 的对象时读取和写入均不成功 |
| 2. 手动配送闭环 | 复用已有订单和结算规则，从真实数据库确认出单、送达、对账、收款和更正 | A/B/C 原样例订单 ¥539，B 少送 3 袋后应收 ¥240。A 收到 ¥100 时分配 ¥60 和 ¥40，补 ¥124 后结清。更正后应收 ¥220、实收 ¥164、欠 ¥56 |
| 3. 故障与并发 | 请求重试、版本冲突、事务回滚和备份恢复 | 响应丢失后重试只记一笔。并行确认或修改不会覆盖新版。模拟收款中途失败后，收款和分配均无新增。恢复到隔离库后金额、快照及分配关系一致 |
| 4. 手机试用 | 微信真实身份、独立环境、材料上传和状态查询 | 两个微信账号用手机互相隔离。同一账号重进可恢复。中断上传可恢复，材料只显示在归属账号，过期结果不会写进新草稿 |
| 5. 补充记账分支 | 按第 5 节实现收款冲销重记、超额款挂账及更正后保留原分配 | 使用第 5 节账例和有后续收款的独立例验收，通过后再开放真实记账 |

实施进度和下一步在[开发任务](开发任务.md)更新。
