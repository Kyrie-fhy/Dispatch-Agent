# S5 本地服务联调

本页用于独立验证 S5 服务端接口，使用两个本地开发账号。先从[开发任务](开发任务.md#当前交付)确认包含相关接口的分支。CI 使用 PostgreSQL 18，API 仅监听 `127.0.0.1`。登录工作区页面和真机验收见 [S5 微信试用](S5微信试用.md)，异地试用见 [HTTPS 部署步骤](S5试用部署.md)。

## 1. 初始化数据库

用本机 PostgreSQL 的管理员账号创建独立数据库 `dispatch_local` 和普通登录角色 `dispatch_local`。把下面的连接地址换成自己的本地配置。

```sh
npm ci
export DISPATCH_DB_ADMIN_URL='postgresql://postgres:管理员密码@127.0.0.1:5432/dispatch_local'
DISPATCH_SERVER_MODE=local npm run db:migrate
psql "$DISPATCH_DB_ADMIN_URL" -c 'GRANT dispatch_app TO dispatch_local'
```

**通过标准**　输出「PostgreSQL 迁移已完成」。重复执行迁移保留现有数据。

## 2. 启动本地服务

```sh
export DISPATCH_DB_URL='postgresql://dispatch_local:本地账号密码@127.0.0.1:5432/dispatch_local'
DISPATCH_SERVER_MODE=local npm run serve:local
```

**通过标准**　服务以普通数据库账号启动，默认监听 `http://127.0.0.1:8787`。下文的 `a`、`b` 开发登录使用「开发会话」，启动它时保持 `DISPATCH_WECHAT_APP_ID` 和 `DISPATCH_WECHAT_APP_SECRET` 均未设置。可通过 `DISPATCH_API_PORT` 修改监听端口。含 [PR #16](https://github.com/Kyrie-fhy/Dispatch-Agent/pull/16) 的分支可以请求 `GET /healthz`，数据库就绪时返回 `200` 和 `{"status":"ready"}`。

## 3. 用测试账号拿到草稿

1. 向 `POST /v1/session/development` 发送 JSON `{"account":"a"}`，响应为 201，包含 `token` 和过期时间。换成 `b` 可获取另一个账号的凭证。
2. 向 `GET /v1/workspace` 发送 `Authorization: Bearer <token>`，响应中的 `draft` 包含服务器分配的 `id`、`revision` 和 `customers`。A、B 的草稿 ID 各不相同。
3. 向 `PUT /v1/drafts/{id}` 发送带凭证的 JSON，包含请求编号 `requestId`、上一版 `revision` 和编辑后的 `customers`。保存成功后修订号加一。
4. 重启服务，用同一测试账号重新登录，再获取工作区。该账号上次保存的客户和修订号仍在。换成另一个账号的凭证访问原草稿 ID，读取和更新均返回 404。
5. 请求 `DELETE /v1/session` 后，原凭证访问草稿返回 401。

## 4. 从草稿预览到取货

1. 在草稿里录入各客户和货品。A 录安井水饺 2 箱，每箱 ¥82。B 录安井水饺 3 箱，每箱 ¥80，另有 3 袋，每袋 ¥20。C 录三全水饺 1 箱，每箱 ¥75。均使用 500g 规格，首次出单的客户在 `partyId` 填 `null`。
2. 向 `POST /v1/trips/preview` 发送 `draftId`、最新 `revision` 和 `requestId`。预览合计为 **53900 分**，返回 `previewId`。此时 `GET /v1/trips/{draftId}` 返回 404，也没有新建客户。
3. 向 `POST /v1/trips/confirm` 发送 `previewId` 和新的 `requestId`。正式单为第 1 版，所有明细初始为「未配送」。若先修改过草稿，旧预览确认返回 409，需要按最新版本重新预览。
4. 用同一请求编号重试确认，再通过 `GET /v1/trips/{draftId}` 查询。仍是同一张正式单。取货汇总为安井 **5 箱、3 袋**，三全 **1 箱**。
5. 向 `POST /v1/trips/next-draft` 发送已确认的 `draftId` 和新的 `requestId`。服务创建空草稿。上一趟正式单和取货清单还可以查询，直到下一趟正式确认，工作区才会切换当前趟。新草稿可用工作区 `parties` 中的 ID 关联已有客户。同名客户仍可明确新建。

所有请求使用第 3 节拿到的凭证。每次新操作换一个请求编号。同一次提交超时重试时沿用原编号和内容。

## 5. 运行集成检查

`DISPATCH_TEST_ADMIN_URL` 应指向本机测试 PostgreSQL 的管理员数据库。检查会创建带随机名称的临时库及普通角色，结束后清理。备份恢复用例使用 `pg_dump` 和 `pg_restore`，建议采用与服务端相同的主版本。将工具加入 `PATH`，或用 `DISPATCH_TEST_PG_BIN` 指定所在目录。CI 使用 PostgreSQL 18 测试容器内的工具。[pg_dump](https://www.postgresql.org/docs/18/app-pgdump.html) · [pg_restore](https://www.postgresql.org/docs/18/app-pgrestore.html)

```sh
DISPATCH_TEST_ADMIN_URL='postgresql://postgres:管理员密码@127.0.0.1:5432/postgres' npm run test:server
```

| 检查 | 通过标准 |
|---|---|
| 账号隔离与恢复 | A、B 分别保存并重启恢复。API 不返回其他账号的草稿，数据库行权限也限制读取和更新。退出后原凭证失效 |
| 并行、重试与回滚 | 同版并行保存只有一笔成功。相同请求重试返回第一次结果，改内容后复用编号返回冲突。故意让第二次数据库写入失败时，草稿保留原版，恢复后可重试 |
| 预览、确认与取货 | 升级保留已保存草稿。预览不出单。改价后旧预览失效，同一预览并行确认只出一张。正式单重启后可查，取货分三行。切换新草稿后仍可查询原单，已有客户 ID 可以复用 |
| 出单失败与恢复 | 正式提交最后一步写入失败时，正式版本、客户、单据关联和工作区一起回滚。原草稿可继续编辑，重试原确认只出一次 |
| 部分送达与客户单核对 | B 只交付 3 箱时，应收为 24000 分，未配送的 3 袋不计入应收。服务重启后状态和核对标志仍在，整趟订单金额及取货汇总保持原值 |
| 核对后修改配送 | 先预览应收差额再确认，旧修订和跨客户单预览被拒绝；并发更新同一修订只有一次成功，写入失败时状态与核对标志能回滚 |
| 旧欠款与跨单收款 | A 收到 ¥100 时先抵 ¥60 旧欠款，再抵本单 ¥40，补 ¥124 后结清。同一客户有两趟正式单时，后单发起的收款优先抵较早的单 |
| 收款一致性 | 确认前账目变化会使旧预览失效，重试或并发确认同一预览只记一次，分配写入失败时连同收款一起回滚。重启后可重新查询分配和余额 |
| 正式单更正 | 预览列出货品、应收和取货的变化。更正历史单生成一个版本，原实收保留。过期、跨账号和写入失败均保留当前正式版本 |
| 备份恢复 | 在临时源库建两套测试账号数据，备份 `dispatch` schema 并恢复到同一测试实例里的独立空库。用新的普通角色启动恢复库服务，核对版本、配送、金额、收款分配、行权限和确认重试 |

## 6. 按明细送达与核对

同一测试账号登录后，以下操作从 `/v1/trips/{tripId}/sheets/{sheetId}` 开始。客户单 ID 从正式单 `sheets` 中取得，作为 URL 路径参数时需编码。

| 方法与相对路径 | 请求和结果 |
|---|---|
| `GET` 客户单 | 返回 `sheet`，含正式单 `version`、配送 `statusRevision`、`reviewed`、`orderCents`、带配送状态的 `lines` 和 `amounts` |
| `POST /delivery` | 传 `requestId`、`version`、`statusRevision`、`lineId` 和 `status`。单行可设 `delivered` 或 `pending`；`lineId: null` 只用于将本客户全部设为 `delivered`。成功返回更新后的 `sheet` |
| `POST /review` | 看过未配送明细后，传 `requestId`、`version` 和 `statusRevision`，确认核对。返回 `reviewed: true` 的 `sheet`；未配送明细仍保留原状态 |
| `POST /delivery/preview` | 需要修改已核对单时，传与 `/delivery` 相同的字段。返回含 `previewId`、目标操作及变更前后金额的 `preview`，配送状态保持原值 |
| `POST /delivery/confirm` | 传 `requestId` 和 `previewId`。预览只适用于原账号、原客户单及原版本与配送修订，成功后返回 `sheet` |

用第 4 节的样例，只将 B 的箱装行标记为 `delivered`，保留袋装行为 `pending`，再核对。B 的订单金额为 **30000 分**，`amounts.due` 为 **24000 分**，取货仍包含 3 袋。应收在核对前用于估算，用 `reviewed` 区分是否核对。`amounts` 的金额单位为分，字段为 `due`（应收）、`paid`（实收）、`remaining`（剩余）和 `excess`（多收）。`paid` 来自已保存到本单的收款分配。

配送修订号在同一趟共享。收到 `delivery_changed` 后重新读取客户单再核对；同一次写入超时则沿用原请求编号和内容重试。

## 7. 补录旧欠款与跨单收款

以下路径接在 `/v1/trips/{tripId}/sheets/{sheetId}` 后。输入 `amount` 为人民币元的字符串，输出金额均为整数分。

| 方法与相对路径 | 请求和结果 |
|---|---|
| `GET /ledger` | 返回 `ledger`，包含同一客户的已核对债项、旧欠款、收款及分配。`otherRemainingCents` 为除当前单以外的剩余欠款 |
| `POST /opening/preview` | 传 `requestId`、`amount`、`day`（`YYYY-MM-DD`），可选 `source`。同一客户的相同日期、金额和来源只能补录一次 |
| `POST /opening/confirm` | 传 `requestId` 和 `previewId`（上一步的 `preview.id`），确认后生成独立的 `opening` 债项 |
| `POST /receipt/preview` | 从已核对单发送 `requestId` 和 `amount`，返回 `preview`，含逐笔分配和分配后余额。超出可抵扣金额时返回当前最多可抵扣金额 |
| `POST /receipt/confirm` | 传 `requestId` 和 `previewId`，返回 `receipt` 及分配。收到 `ledger_changed` 后重新预览。同一次确认超时后沿用原请求编号和预览编号 |

用第 4 节的 A 客户样例，将本单标记送达并核对，补录日期早于本单的 ¥60 欠款。确认 ¥100 收款后，旧欠结清，本单实收 ¥40、剩余 ¥124。再确认 ¥124 后，本单累计实收 ¥164、剩余为 0。

## 8. 正式单更正

以下路径接在 `/v1/trips/{tripId}/sheets/{sheetId}` 后，可指定当前或历史客户单。

| 路径 | 请求和结果 |
|---|---|
| `POST /amendment/preview` | 传 `requestId`、`version`、`statusRevision` 和更正后的完整 `items`。沿用原明细 `id` 修改数量或单价。替换已送达货品时，在 `replacementStatuses` 提供该行的 `delivered` 或 `pending`。返回 `previewId`、明细及其状态差异、取货差异和更正前后的金额 |
| `POST /amendment/confirm` | 传 `requestId` 和 `previewId`，返回新 `version`。旧预览返回 `amendment_changed`，需读取最新单据再预览。重复确认同一预览返回已保存的版本 |

A 本单累计实收 ¥164 后，将原来的 2 箱单价从 ¥82 改为 ¥110。预览时仍可查询第 1 版。确认后查第 2 版，显示应收 ¥220、实收 ¥164、欠 ¥56。原明细仍为已送达，原收款分配可在 `/ledger` 查询。

## 9. 备份恢复验收

运行第 5 节的 `npm run test:server`。用例通过 HTTP 生成 A/B/C 配送趟、B 部分送达和 A 的旧欠款、两次收款及正式单更正。测试记录读数后停止源库的应用服务，生成自定义格式归档。恢复目标从 `template0` 创建，用 `pg_restore --single-transaction --no-owner` 导入，保留表和行权限，使用集群已有的 `dispatch_app` 角色及新建的普通登录角色启动应用。归档只在测试进程内保存。

恢复后比较同一正式趟的两版快照、取货、配送状态和完整收款记录。应读到 A 应收 ¥220、实收 ¥164、欠 ¥56，B 应收 ¥240。有各自账本的两个测试账号登录成功。B 直接查询库或通过 API 均无法访问 A 的正式单，重发 A 已确认的收款或更正返回原结果。

## 10. 材料上传和续传

上传接口使用工作区的会话凭证。每个文件最多 10 MiB，每块 256 KiB，最后一块为剩余字节。文件包括 JPG、PNG、WebP、HEIC，以及 MP3、M4A、AAC、WAV、OGG、AMR、SILK。

| 方法 | 请求与返回 |
|---|---|
| `POST /v1/materials` | 传 `requestId`、活动 `draftId`、`revision`、文件 `name`、字节数 `size` 和小写十六进制 SHA-256 `digest`。成功返回 201 和 `material`。用同一请求编号重试可恢复已登记的材料。 |
| `GET /v1/materials`、`GET /v1/materials/{id}` | 查询本账号的上传记录。返回状态 `uploading` 或 `ready`、已提交字节数 `received` 和草稿是否仍是当前未确认修订 `draftCurrent`。 |
| `PUT /v1/materials/{id}/chunks` | 请求体为原始字节，`Content-Type: application/octet-stream`，`X-Material-Offset` 为起始字节。提交后返回本次进度。重发同一位置和同一字节返回已保存进度。 |

请求中断后先读 `received`，再从该位置发送原文件。重复位置带不同字节、完整文件摘要不符或跳发分块会失败，已提交分块保留。最后一块和全部文件校验在同一事务内完成。

归属由会话和数据库行权限共同限定。另一个账号读取或写入材料编号返回 404。旧草稿修订不能登记新材料，已登记的材料仍可续传到原草稿，`draftCurrent` 返回 `false`。上传不会编辑草稿。私有文件分块随 `dispatch` schema 归档和恢复。
