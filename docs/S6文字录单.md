# S6 文字录单与评测

S6 复用 S5 的工作区、取货、送达和单据更正服务。配送 MVP 首页是「录单、取货、送货」。图片上传从录单进入，图片识别和语音转写留在 S7。本次应收按已送达明细计算；一条只送了部分数量时，可更正为实际送达数量后再标记。收款及旧欠款继续保留在 S5 构建。

## 启动和验收

1. 按 [S5 本地联调](S5本地联调.md) 配好 PostgreSQL，运行 `npm run db:migrate`，应用 `007_text_order_inputs.sql`。小程序仍按 [微信工作区联调](S5微信试用.md#正式页面本机联调) 配置测试号。
2. 将 DeepSeek API 密钥注入服务端进程的 `DISPATCH_TEXT_MODEL_KEY`，再运行 `npm run serve:local`。默认模型为 `deepseek-flash`，可通过 `DISPATCH_TEXT_MODEL` 指定同一接口的模型。未配置密钥时，文字整理返回暂未开启，仍可手动编辑和出单。密钥只由服务端读取。模型接收本次文字和当前草稿用于定位明细的字段，不接收会话、历史账目或图片。[DeepSeek JSON Output](https://api-docs.deepseek.com/guides/json_mode/)
3. 运行 `npm run build:s6` 后，用微信开发者工具重新编译。从「录单」输入「老王要两箱安井水饺 500g」，点「整理到草稿」。确认单价停在待补齐，输入「单价82元一箱」后核对草稿。若账号已有同名客户，先手动选定该客户或明确新建。
4. 「预览整趟」应为 ¥164，此时还没有正式单。点「确认生成正式单」后，取货显示 2 箱；在「送货」打开老王的客户单，未送达为 ¥0，标记送达后本次应收为 ¥164。

## 服务边界

`POST /v1/text-orders` 使用工作区凭证，接收 `{requestId, draftId, revision, text}`，成功返回 `{draft}`。服务先读取对应账号及草稿修订，调用模型，再在工作区事务中核对修订并提交。模型等待期间不会锁住草稿。当前趟已确认、草稿被修改或会话已退出时，过期结果不写入草稿。

模型只能提出新增明细或补空字段。数量追加、覆盖已填值和无法定位的补充交给人工处理。缺字段保留为空，编辑区集中列出问题。重复提交原请求可恢复同版成功结果；同一趟再次提交已录入的同一段文字会提示重复。调用失败时，页面保留本次文字，可以重试或手动填写。模型不执行预览、出单和金额计算。

## 运行最小 Harness

按 [集成检查](S5本地联调.md#5-运行集成检查) 把 `DISPATCH_TEST_ADMIN_URL` 指向隔离的本机 PostgreSQL 实例。用例由临时数据库和空草稿开始，固定输入、人工答案分别记录在 [s6-text-cases.cjs](../tests/fixtures/s6-text-cases.cjs)。

```sh
npm run eval:s6
DISPATCH_S6_EVAL_LIVE=1 npm run eval:s6
```

第一条使用固定模型响应，检查真实 HTTP 和数据库。第二条使用同一人工答案实际调用 DeepSeek；先在执行进程配置 `DISPATCH_TEXT_MODEL_KEY`。单次真实评测计划最多四次调用，单次输出最多 2500 tokens，无自动重试。先只用固定合成账例，把首轮实际用量记下来，再定试用额度。价格按 [DeepSeek 官方报价](https://api-docs.deepseek.com/quick_start/pricing/)核算。

测试输出含运行 ID、用例和提示版本、执行模式、工具结果及规则评分。真实模式还记录服务返回的模型、请求 ID、耗时、token 使用量，以及服务返回时的模型指纹。凭证不出现在日志中。分数只覆盖该用例，用例失败时以最后一个未通过的规则定位问题。
